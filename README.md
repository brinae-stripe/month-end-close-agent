# Month-End Close Agent

An illustrative, fully offline demo of an internal AI reconciliation console
a single-family-rental property manager might build on top of their Stripe
Connect data.

**All data in this demo is synthetic.** Entity names, resident IDs, property
IDs, transaction IDs, and dollar amounts are generated by a seeded random
process (`generate_data.py`). Nothing here reflects a real company, a real
Stripe account, or a real person. Every object ID carries a `DEMO` marker
(`acct_DEMO_...`, `ch_DEMO_...`, `po_DEMO_...`, etc.) to make this
unmistakable.

## What it is

- Four views: **Close** (month-end reconciliation board), **Ask** (a
  scripted, non-generative Q&A panel), **Margin** (absorbed card-fee
  cost made visible), and **Residents** (tenant/lease-level payment
  behavior, sourced only from fields documented at
  [docs.stripe.com/data/schema](https://docs.stripe.com/data/schema):
  on-time/late/NSF rent payment rates, lease renewal and rent-increase
  rates, security deposit held/refunded/withheld totals, and rent-charge
  dispute rate, on a weighted sample of 480 synthetic leases. Its
  "Rule-Based Risk Flags" panel is a deterministic point-scoring pass over
  that same payment history, run in the browser — like Ask, it is
  explicitly not a language model and makes no network call. Each flagged
  lease shows the resident, not the property-owner entity, as the subject,
  with a simulated recommended action (send reminder, retry debit, escalate
  dispute) styled after a Stripe MCP-connected agent — illustrating what's
  possible, not a real Stripe call.
- Modeled on **81 connected accounts**: 64 active entities in scope for
  the current month's reconciliation (~$92M of rent volume across
  ~47,000 homes and ~44,000 charges) plus 17 dormant entities carried for
  lifetime-volume context only, excluded from the current-month
  reconciliation math. Every entity, exception, and headline number is
  computed from generated data — nothing is hardcoded.
- Six seeded exception types (NSF-after-payout, stale entity mapping,
  application-fee misroute, short payment, duplicate payment, failed
  payout) that the exception queue on the Close view walks through.
  Payouts that can no longer clear by the 10th even if fixed today are
  flagged **"unrecoverable by deadline"**, distinct from payouts that are
  merely late — this is a computed comparison against the T+2 settlement
  cutoff (last day to initiate: the 8th), not an arbitrary label.
- Payments flow as **Stripe Connect destination charges**: the platform
  is merchant of record, funds transfer to the connected account at
  charge time, and the platform pays Stripe under its own negotiated
  rate. Every charge and every entity rollup shows all three amounts —
  gross, fee, and net — rather than collapsing to a single total.
- The "Ask" panel is **not** wired to any language model. Its six suggested
  questions and free-text fallback are scripted; every answer is computed
  from the same JSON the other two views read, so the numbers always agree
  across views.
- Fee assumptions on the Margin view use this operator's **negotiated
  Connect pricing** (2.50% + $0.20 domestic card, 4.00% + $0.20
  international card, ~1% of card volume assumed international). ACH
  pricing (0.80%, capped at $5.00) is an unverified placeholder, flagged
  as such on screen. Digital wallet payments are assumed to be priced
  identically to domestic card — a labeled assumption, not a
  Stripe-verified rate — and the processing fee is modeled as netted from
  the investor's transfer rather than absorbed by the operator, also an
  unconfirmed assumption. The Margin view also shows a subordinate
  "ceiling" figure: the maximum possible exposure if every card fee were
  absorbed instead of passed through, so the actual absorbed-cost
  headline can be read against a bound rather than in isolation.
- A persistent assumptions panel above the footer lists every unverified
  or assumed figure on screen at all times, so nothing is presented as
  more certain than it is.

## Running it

```
./run.sh
```

This regenerates `web/data/reconciliation.json` from the seeded generator
and starts a local static file server, then opens the demo in Chrome at
`http://localhost:8420/`. No build step, no `npm install`, no network
calls at runtime — everything is stdlib Python plus vanilla HTML/CSS/JS.

To use a different port: `PORT=9000 ./run.sh`.

To regenerate the data without starting the server:

```
python3 generate_data.py
```

## Deploying to Vercel

The app is a static site rooted at `web/`, with `web/data/reconciliation.json`
pre-generated and committed — there's no build step. `vercel.json` sets
`outputDirectory: "web"` so Vercel serves that directory directly instead of
the repo root. No other configuration is required; just import the repo into
a Vercel project and deploy.

To pick up new synthetic data on a deploy, run `python3 generate_data.py`
locally, commit the updated `web/data/reconciliation.json`, and push.

## Resetting between sessions

The "Approve" and "Send to review" actions on the Close view are in-memory
only — nothing is written to disk. Reloading the page (or restarting
`run.sh`) returns the demo to its initial state. Because the generator is
seeded, every run produces byte-identical data.

## Layout

```
generate_data.py       synthetic data generator (Python stdlib only)
web/
  index.html
  styles.css
  app.js               shared state: data loading, tab switching, live approval state
  close.js             Close view
  ask.js                Ask view (scripted Q&A)
  margin.js             Margin view
  residents.js          Residents view (tenant/lease stats + risk-scoring pass)
  svg-charts.js         inline-SVG line chart helper (no charting library)
  data/reconciliation.json   generated output (not hand-edited)
run.sh                 regenerate data + launch
```
